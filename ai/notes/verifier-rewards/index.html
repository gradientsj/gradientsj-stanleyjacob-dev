Deterministic verifiers as reward functions

Notes · post-training against evaluation infrastructure · August 2026

These are working notes for the post-training milestone of my agent evaluation platform: taking Qwen3.6-27B through rejection-sampling SFT and then GRPO, where the reward at every step is the same deterministic verifier the evaluation harness reports with. The training pipeline pieces described here are implemented and tested offline; the GPU loop itself is queued behind the serving infrastructure, and I say below exactly which is which.

The core move: the metric you train against is the metric you report

Most RLHF-adjacent pipelines optimize a proxy — a learned reward model, an LLM judge — and then evaluate on something else, which is how you get models that improved on the reward and regressed on the task. The evaluation platform bans LLM judges from the scoring path entirely: extraction is scored by field-level F1 against generated gold labels, reasoning by exact programmatic checks, code by unit tests in a restricted subprocess. Every one of those is a pure function from (task, completion) to a score in [0, 1]. That has an immediate consequence for post-training: the verifier IS the reward function. No reward model to train, no judge to flatter, no proxy gap between what the optimizer sees and what the benchmark reports. The adapter is ~40 lines: bind a benchmark's verifier, feed it (case, completion), return the score as reward.

The verifier scores are also usefully dense where it matters: extraction F1 gives partial credit per field, so GRPO groups aren't all-zero on hard cases the way strict pass/fail rewards tend to be, while code stays honestly binary (pass@1) because pretending test outcomes are continuous would be dishonest.

Rejection-sampling SFT, mined from evaluation artifacts

Rejection sampling here is literal: only completions that pass the deterministic verifier become training targets. Because the platform persists every rollout — prompt, output, verifier result, every repair turn — the first SFT dataset comes free from runs that already happened, rather than from a separate generation job. The miner regenerates cases deterministically from the run manifest, re-verifies every candidate completion at mining time (a benchmark-version drift fails loudly instead of silently mislabeling data), and emits three kinds of examples:

  • solve — first-attempt passes: (task, verified answer);
  • repair_final — the corrected answer after failed attempts, presented as a direct answer to the original task;
  • repair_transcript — the full conversation: wrong answer → verifier feedback → verified fix. This is the training signal for "steer solvers toward verified fixes," and two details matter. The feedback is answer-free by contract (it names which fields are unsupported, never the correct value — a property with its own regression test, because an early version leaked "must be null" and a review pass caught it). And the repair turn's wording comes from the same function the inference loop uses, so training transcripts match deployment byte-for-byte.

Pipeline validation on an existing offline run (mock models, so free and deterministic): 61 verified examples — 37 solve, 12 repair_final, 12 repair_transcript — with zero re-verification failures. At real scale the same command runs against the full benchmark run's artifacts, and best-of-n sampling at temperature slots in as a second source for cases no model solved.

GRPO over verifier scores

GRPO fits this setting well: sample a group of completions per task, score each with the verifier, and use group-relative advantages — no value network, no learned critic, and the reward is exactly the benchmark metric. The plan (queued behind the GPU serving milestone) is standard: SFT checkpoint as the starting policy, groups of 8–16 completions per case, verifier score as raw reward, KL penalty to the SFT policy. Everything that feeds it — prompt construction, the reward lookup keyed by prompt for TRL/verl-style trainer loops, case splits — is implemented and tested. I'm deliberately not publishing training hyperparameters I haven't run.

Reward hacking, and why "a different seed" is not a defense

Optimizing against a fixed verifier invites the model to learn the verifier rather than the task: format tricks, distribution quirks of the generator, anything that raises score without raising competence. The defense uses the platform's adversarial machinery against its own training loop:

  • training rewards come from visible cases only;
  • a hidden split — adversarial derivatives of the same clean tasks, generated with a held-back seed and validated by the same deterministic validator — is never exposed to training and gets evaluated post-hoc;
  • the alarm is the gap: if visible pass rates climb while hidden pass rates stall or fall, the model is learning the verifier, not the task.

Writing the disjointness test surfaced the kind of bug these notes exist to remember: a different random seed does not guarantee different data. Some adversarial operators are low-entropy — a delimiter swap has three choices; a paragraph shuffle on a short document has a small permutation space — so two seeds can produce byte-identical mutations, silently leaking "hidden" tests into training data. The fix is to enforce rather than assume: hidden candidates are collision-filtered against the actual training documents, and a test asserts the filter fires on real collisions. Disjointness is a property you check, not a property you get from seeding discipline.

The measurement protocol for [X] → [Y]

The claim worth making at the end is "post-training lifted held-out pass@1 from X to Y," and both numbers need to survive scrutiny. X is the best steered-prompt baseline: the strongest configuration achievable without touching weights (repair loop on, best-of-n), measured by the harness on held-out cases. Y is the post-trained checkpoint served through the identical OpenAI-compatible adapter and measured by the identical verifiers on the identical splits — plus the hidden adversarial set, which the baseline also runs so the reward-hacking comparison is apples-to-apples. Until that experiment runs, these notes contain no X and no Y; when it runs, both come out of persisted rollout artifacts with run IDs attached, like every other number the platform publishes.
