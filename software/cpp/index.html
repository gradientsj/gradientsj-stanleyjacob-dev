C++ from object lifetime to optimal algorithms.

Language field guide · C++11 → C++26 · Standards status verified Jul 27, 2026

Evergreen reference · interview and systems focus

C++ becomes much easier when every feature is connected to one question: what object exists, who owns it, and what can observe it? This guide builds that model first, follows the language from C++11 through the frozen C++26 feature set, then applies it to LeetCode-style problems by moving deliberately from a correct baseline to the best justified implementation.

The working model: objects, storage, lifetime, and observable behavior

C++ is not “C with classes,” and modern C++ is not a contest to use the newest syntax. It is a language for building abstractions whose cost and resource behavior remain visible. A useful abstraction expresses ownership, makes invalid states difficult to represent, releases resources deterministically, and compiles to work close to what a careful low-level implementation would perform.

Storage is not lifetime

Bytes can exist before an object is constructed in them and after its destructor runs. A pointer may still contain an address while no live object may legally be accessed there.

Types carry contracts

T owns a value, T& borrows a required object, T* commonly represents optional or iterator-like access, and smart pointers state dynamic ownership.

Undefined behavior is optimizer permission

Out-of-bounds access, signed overflow, dangling use, invalid shifts, and data races do not promise a friendly runtime error. They remove constraints on the generated program.

Zero-cost does not mean free

It means you do not pay for facilities you do not use and a well-designed abstraction need not cost more than an equivalent hand-written mechanism. Allocation, indirection, and cache misses still cost what the machine charges.

The translation model still matters

A source file is preprocessed and compiled into a translation unit. Object files are then linked. Headers traditionally copy declarations and definitions into each including translation unit. Templates usually need their definitions visible where they are instantiated. The One Definition Rule constrains which definitions may appear once in the program and which identical definitions may appear across translation units. Modules improve this model, but mixed build systems and libraries mean headers will remain relevant for a long time. 

g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic app.cpp -o app
g++ -std=c++20 -O1 -g -fsanitize=address,undefined app.cpp -o app_asan
g++ -std=c++20 -O1 -g -fsanitize=thread -pthread concurrent.cpp -o app_tsan

For interviews, choose the newest standard the environment confirms. C++17 or C++20 is a safe practical target. Name the standard feature you rely on. A brilliant C++23 solution is not useful if the judge compiles as C++17.

Ownership, RAII, value categories, and special members

RAII (Resource Acquisition Is Initialization) ties a resource to an object's lifetime. The constructor establishes an invariant. The destructor releases the resource on normal return and during stack unwinding. The resource might be memory, a file descriptor, a lock, a socket, a transaction, or a subscription.

Type at an interface Usual meaning Question to ask
T Owned value. Copy or move into the callee. Is taking ownership or making a copy intended?
const T& Required read-only borrow for this call. Can the reference escape or outlive its source?
T& Required mutable borrow. Is mutation obvious from the function's purpose?
T* Often optional/non-owning or array-like access. May it be null, and what bounds/lifetime apply?
unique_ptr<T> Exclusive dynamic ownership. Why is dynamic allocation required?
shared_ptr<T> Shared lifetime through a control block. Does the domain really have shared ownership?
weak_ptr<T> Non-owning observation of shared state. What happens if promotion fails?
span<T> Borrowed contiguous sequence with a size. Who keeps the elements alive?

Rule of Zero first. Rule of Five only when the class truly manages a resource

If every member already manages itself, define none of the destructor, copy constructor, copy assignment, move constructor, or move assignment. That is the Rule of Zero. A class that manually owns a resource may need all five. Copy-and-swap is a compact route to strong exception-safe assignment. 

rule_of_zero.cppclass Packet {
public:
    Packet(std::uint64_t sequence, std::vector<std::byte> bytes)
        : sequence_(sequence), bytes_(std::move(bytes)) {}

    // No destructor, copy, or move declarations. vector owns its storage.
    std::span<const std::byte> payload() const noexcept { return bytes_; }

private:
    std::uint64_t sequence_;
    std::vector<std::byte> bytes_;
};

std::move is a cast, not an operation

An lvalue identifies a persistent object. An xvalue identifies an object whose resources may be reused. A prvalue computes a value. std::move(x) casts x to an xvalue so move overloads become eligible. The selected constructor or assignment does the work. A moved-from standard-library object remains valid but usually has an unspecified value.

Interview invariant

After a move, destruction and assignment must remain safe. Do not assume any stronger state unless the type documents one. Prefer return local; over return std::move(local); so copy elision remains available.

Views borrow. They do not extend lifetime

dangling.cppstd::string_view broken() {
    std::string local = "temporary";
    return local;                     // dangling after return
}

std::span<const int> also_broken() {
    std::vector<int> local{1, 2, 3};
    return local;                     // span does not own the vector
}

The same reasoning applies to iterators, references captured by asynchronous callbacks, and pointers into a vector that later reallocates. Most C++ memory defects are lifetime mistakes wearing different syntax.

Static polymorphism, concepts, and runtime polymorphism

Templates produce code specialized for types and expose optimization opportunities. Virtual interfaces choose behavior at runtime. std::variant represents a closed set of alternatives. Type erasure such as std::function hides the concrete type behind a value-like interface. Choose based on whether the set of types is open, when the choice is known, binary boundaries, code size, and ownership, not on fashion.

Mechanism Best fit Main tradeoff
Template / concept Choice known at compile time. Performance-sensitive generic code. Instantiation cost, diagnostics, code size, header exposure.

variant + visit Closed family where exhaustive handling is useful. Largest-alternative storage and recompilation when the set changes.

Const, constexpr, consteval, and noexcept answer different questions

  • const T restricts mutation through that expression.
  • A const member function treats *this as const, except for mutable members.
  • constexpr permits constant evaluation when inputs and operations allow it. It does not force every call to compile time.
  • consteval requires an immediate, compile-time invocation.
  • noexcept states that exceptions will not leave the function. Violating it terminates the process.

A truthful noexcept move constructor matters because containers can move elements during reallocation only when doing so preserves their exception guarantee. Otherwise they may copy.

Containers, locality, invalidation, and the data structure behind the Big-O

Start with vector. Its contiguous storage makes iteration and indexing cheap, and modern processors reward locality. Choose another container when an actual invariant requires stable references, sorted traversal, fast ends, or key lookup.

Container Typical operations Invalidation / interview note
vector Index O(1), end push amortized O(1), middle insert O(n). Reallocation invalidates every pointer, reference, and iterator into it.
deque Ends O(1), index O(1), non-contiguous blocks. Ideal for a monotonic queue. Invalidation rules are subtler than vector.
list Known-position insert/erase and splice O(1). Stable iterators, but allocation and poor locality make it a specialized choice.
unordered_map Expected O(1) lookup/insert/erase. Worst case O(n). Rehash invalidates iterators, not references to elements.
map Ordered O(log n) operations. Stable node references. Supports lower/upper bounds and ordered traversal.
priority_queue Top O(1), push/pop O(log n). Only the extreme is visible. Excellent for top-k and frontier problems.
array Fixed-size contiguous value. No allocation. Size belongs to the type and is known at compile time.
span Non-owning contiguous view, O(1) construction. Never extends lifetime. Use it to make pointer-plus-length explicit.

Ranges improve composition, not asymptotic complexity

ranges.cppstd::vector<int> values{7, 2, 9, 4, 1, 6};

auto even_squares =
    values
    | std::views::filter([](int x) { return x % 2 == 0; })
    | std::views::transform([](int x) { return x * x; });

for (int value : even_squares) {
    std::cout << value << '\n';   // lazy: 4, 16, 36
}

Views are often lazy and borrow their source. That can avoid intermediate allocations, but it also means a view can dangle and repeated traversal can repeat work. “Modern” syntax does not remove the need to reason about cost and lifetime.

Errors, concurrency, testing, and the tools that make C++ reliable

Choose an error channel that matches the contract

  • Return a value when failure is not part of the domain.
  • Use optional<T> for value-or-absence without an error reason.
  • Use expected<T, E> or a project equivalent for a typed, expected failure.
  • Use exceptions for failures that cannot be handled locally when the codebase permits them.
  • Use assertions for programmer invariants, not recoverable input errors.

Know the exception guarantees: no-throw, strong (failure has no observable effect), basic (invariants survive), and no guarantee. Destructors should not let exceptions escape.

Concurrency starts with a shared-state contract

A data race is undefined behavior. volatile does not provide atomicity or inter-thread ordering. Begin with a mutex around a compound invariant. Use condition variables with predicates. Move to atomics only when the ownership and happens-before edges are precise. The separate practical C++ multithreading guide develops queues, thread pools, atomics, acquire/release ordering, parallel algorithms, a lock-free SPSC ring buffer, and debugging.

Compiler warnings

-Wall -Wextra -Wpedantic -Wconversion -Wshadow expose suspicious conversions, hiding, and portability mistakes.

Sanitizers

ASan finds invalid memory access. UBSan instruments undefined operations. TSan observes data races. Run race and address builds separately.

Static analysis

clang-tidy and compiler analysis catch ownership, API, modernization, and bug patterns that tests may not execute.

Tests and fuzzing

Boundary tests protect known contracts. Property and differential tests compare optimized code with a small brute-force oracle.

The interview method: baseline, bottleneck, invariant, optimization

Do not begin with the clever solution. A small correct baseline proves understanding, gives a complexity target, and often becomes a differential-test oracle. Optimization should remove one named piece of repeated work.

  1. Clarify. Input bounds, mutation, duplicates, ordering, failure representation, and which resource matters.
  2. Build a baseline. The direct nested loop, full sort, repeated traversal, or linear lookup.
  3. Name the bottleneck. “For every right endpoint, I rescan the window for its maximum.”
  4. State the needed information. “I only need candidates that could still become a maximum.”
  5. Define an invariant. “Indices in the deque are in-window and their values decrease front to back.”
  6. Implement and test. Normal, smallest, duplicate, adversarial, and absence cases.
  7. State the real bound. Expected versus worst-case hashing, amortization, recursion depth, and auxiliary space.
A sentence worth practicing

“The O(n²) baseline repeats this scan. I can replace that scan with this state. After processing index i, the state means this. Therefore each element enters and leaves at most once, which gives O(n).”

Big-O is a model, not a benchmark

A sorted vector can beat a hash table for small inputs. A theoretically inferior algorithm can have lower constants, better locality, deterministic latency, or no allocation. “Optimal” below means the best standard interview approach under the usual problem constraints, not a universal performance result.

Eight worked progressions in interview-ready C++

1. Two Sum: repeated search becomes remembered state

BaselineEvery pair · O(n²)
BottleneckRescan prior values
OptimalHash prior value → index · expected O(n)
Invariant

Before index i, the table contains only values at indices smaller than i. Query before insertion so one element cannot satisfy both positions.

Compare the baseline and hash-map implementations 
two_sum.cppusing Answer = std::optional<std::pair<std::size_t, std::size_t>>;

Answer two_sum_brute(const std::vector<int>& a, int target) {
    for (std::size_t i = 0; i < a.size(); ++i)
        for (std::size_t j = i + 1; j < a.size(); ++j)
            if (static_cast<long long>(a[i]) + a[j] == target)
                return std::pair{i, j};
    return std::nullopt;
}

Answer two_sum(const std::vector<int>& a, int target) {
    std::unordered_map<long long, std::size_t> prior;
    for (std::size_t i = 0; i < a.size(); ++i) {
        const long long need =
            static_cast<long long>(target) - static_cast<long long>(a[i]);
        if (auto it = prior.find(need); it != prior.end())
            return std::pair{it->second, i};
        prior.emplace(a[i], i);
    }
    return std::nullopt;
}

Widen before arithmetic to avoid signed int overflow. Test a duplicate answer such as [3,3], target=6, then no answer, negative values, and extreme representable inputs.

2. Product Except Self: reuse partial products without division

BaselineMultiply all other values · O(n²)
MiddlePrefix + suffix arrays · O(n) space
OptimalOutput prefixes + scalar suffix · O(1) auxiliary
Invariant

After the first pass, out[i] is the product strictly left of i. During the reverse pass, suffix is the product strictly right of i.

O(n) time and O(1) auxiliary space, excluding the output 
product_except_self.cppstd::vector<long long> product_except_self(const std::vector<int>& a) {
    std::vector<long long> out(a.size(), 1);

    for (std::size_t i = 1; i < a.size(); ++i)
        out[i] = out[i - 1] * a[i - 1];

    long long suffix = 1;
    for (std::size_t i = a.size(); i > 0; --i) {
        out[i - 1] *= suffix;
        suffix *= a[i - 1];
    }
    return out;
}

This naturally handles one or multiple zeros. The prompt normally guarantees products fit the chosen type. Production code must define overflow behavior rather than silently relying on signed overflow.

3. Longest unique substring: move the boundary, not every character

BaselineCheck every substring · O(n³)
MiddleSet-based sliding window · O(n)
OptimalLast index jump · O(n), fixed byte table
Invariant

[start, i] contains no repeated byte. The table stores one past each byte's most recent index, so start never moves backward.

Indexed sliding window 
longest_unique.cppstd::size_t longest_unique(std::string_view text) {
    std::array<std::size_t, 256> next_start{};
    std::size_t start = 0;
    std::size_t best = 0;

    for (std::size_t i = 0; i < text.size(); ++i) {
        const auto byte = static_cast<unsigned char>(text[i]);
        start = std::max(start, next_start[byte]);
        best = std::max(best, i - start + 1);
        next_start[byte] = i + 1;
    }
    return best;
}

This solves a byte-string contract. Full Unicode grapheme clusters require decoding and a different key type. Say so if the interface claims human-visible characters.

4. Sliding Window Maximum: discard candidates that can never win

BaselineMax per window · O(nk)
MiddleHeap + stale indices · O(n log n)
OptimalMonotonic deque · O(n)
Invariant

Deque indices are inside the current window and their values strictly decrease from front to back. A newer value at least as large makes an older smaller value permanently irrelevant.

Monotonic deque: every index enters and leaves once 
sliding_max.cppstd::vector<int> sliding_max(const std::vector<int>& a, std::size_t k) {
    if (k == 0 || k > a.size()) return {};

    std::deque<std::size_t> candidates;
    std::vector<int> out;

    for (std::size_t i = 0; i < a.size(); ++i) {
        while (!candidates.empty() && candidates.front() + k <= i)
            candidates.pop_front();

        while (!candidates.empty() && a[candidates.back()] <= a[i])
            candidates.pop_back();

        candidates.push_back(i);
        if (i + 1 >= k) out.push_back(a[candidates.front()]);
    }
    return out;
}

5. Merge Intervals: sorting creates the local structure

BaselineFind and merge any overlapping pair · up to O(n³)
BottleneckOverlaps are discovered out of order
OptimalSort then sweep · O(n log n)
Invariant

The output is sorted and disjoint. Because future starts never decrease, the next interval can overlap only the final accumulated interval.

Sort by start, then extend or append 
merge_intervals.cppstruct Interval {
    int start;
    int end;
};

std::vector<Interval> merge_intervals(std::vector<Interval> intervals) {
    if (intervals.empty()) return {};

    std::ranges::sort(intervals, {}, &Interval::start);
    std::vector<Interval> out{intervals.front()};

    for (std::size_t i = 1; i < intervals.size(); ++i) {
        if (intervals[i].start <= out.back().end)
            out.back().end = std::max(out.back().end, intervals[i].end);
        else
            out.push_back(intervals[i]);
    }
    return out;
}

Clarify whether touching intervals such as [1,2] and [2,3] merge, and reject or normalize intervals whose start exceeds their end.

6. Course Schedule: count prerequisites instead of rediscovering paths

BaselineFresh DFS from every course · O(V(V+E))
AlternativeThree-color DFS · O(V+E)
OptimalKahn indegrees · O(V+E)
Invariant

The queue contains exactly courses with zero remaining prerequisites. Removing one course decrements each dependent once. Finishing fewer than V courses proves a cycle.

Kahn's topological-sort algorithm 
course_schedule.cppbool can_finish(
    std::size_t n,
    const std::vector<std::pair<std::size_t, std::size_t>>& prerequisites) {
    std::vector<std::vector<std::size_t>> dependents(n);
    std::vector<std::size_t> indegree(n, 0);

    for (const auto& [course, prerequisite] : prerequisites) {
        dependents[prerequisite].push_back(course);
        ++indegree[course];
    }

    std::queue<std::size_t> ready;
    for (std::size_t course = 0; course < n; ++course)
        if (indegree[course] == 0) ready.push(course);

    std::size_t completed = 0;
    while (!ready.empty()) {
        const auto course = ready.front();
        ready.pop();
        ++completed;
        for (const auto next : dependents[course])
            if (--indegree[next] == 0) ready.push(next);
    }
    return completed == n;
}

7. Network Delay: nonnegative weights make a frontier node final

BaselineBellman–Ford · O(VE)
ConstraintAll weights are nonnegative
OptimalDijkstra · O((V+E) log V)
Invariant

When the smallest non-stale distance leaves the heap, no later path through nonnegative edges can improve it. Stale heap entries are skipped rather than requiring decrease-key.

Adjacency list plus min-heap Dijkstra 
dijkstra.cppusing Edge = std::pair<std::size_t, int>;
using State = std::pair<long long, std::size_t>;

std::vector<long long> shortest_paths(
    const std::vector<std::vector<Edge>>& graph, std::size_t source) {
    constexpr long long inf = std::numeric_limits<long long>::max() / 4;
    std::vector<long long> distance(graph.size(), inf);
    std::priority_queue<State, std::vector<State>, std::greater<>> frontier;

    distance[source] = 0;
    frontier.emplace(0, source);

    while (!frontier.empty()) {
        const auto [cost, node] = frontier.top();
        frontier.pop();
        if (cost != distance[node]) continue;

        for (const auto& [next, weight] : graph[node]) {
            const long long candidate = cost + weight;
            if (candidate < distance[next]) {
                distance[next] = candidate;
                frontier.emplace(candidate, next);
            }
        }
    }
    return distance;
}

Dijkstra is wrong with negative edges. Bellman–Ford handles them and can detect reachable negative cycles. State the constraint that licenses the optimization.

8. LRU Cache: combine structures whose strengths cover each other's weakness

BaselineVector in recency order · lookup O(n)
NeedFast key lookup + stable O(1) reorder
OptimalHash → list iterator · expected O(1)
Invariant

The list front is most recent, the back is least recent, and every hash entry points to exactly one live list node. Update both structures together.

list::splice moves a node without invalidating its iterator 
lru_cache.cppclass LruCache {
    using Entry = std::pair<int, int>;

public:
    explicit LruCache(std::size_t capacity) : capacity_(capacity) {
        if (capacity == 0) throw std::invalid_argument("zero capacity");
    }

    std::optional<int> get(int key) {
        auto it = index_.find(key);
        if (it == index_.end()) return std::nullopt;
        entries_.splice(entries_.begin(), entries_, it->second);
        return it->second->second;
    }

    void put(int key, int value) {
        if (auto it = index_.find(key); it != index_.end()) {
            it->second->second = value;
            entries_.splice(entries_.begin(), entries_, it->second);
            return;
        }
        if (entries_.size() == capacity_) {
            index_.erase(entries_.back().first);
            entries_.pop_back();
        }
        entries_.emplace_front(key, value);
        index_[key] = entries_.begin();
    }

private:
    std::size_t capacity_;
    std::list<Entry> entries_;
    std::unordered_map<int, std::list<Entry>::iterator> index_;
};

This is not automatically thread-safe. Adding one mutex gives a coherent basic design. Sharding or lock-free work should follow a measured contention problem and a documented consistency contract.

The compact strategy. Default to values, RAII, Rule of Zero, vector, explicit borrowing, and the simplest synchronization that meets the contract. In algorithms, start with a correct baseline and optimize only after naming the repeated work. Modern C++ is not about using every feature. It is about making lifetime, state, and cost legible.
