Practical C++ multithreading

Software & architecture · C++ concurrency · Jul 2026

This is the hands-on companion to my class write-up on concurrency across four languages. That page owns the theory, the C++ memory model, happens-before, and how Rust, C, and Python approach the same problems. This page stays with working C++ that a practitioner can lift into a codebase today. Every sample below compiles with g++ -std=c++20 -O2 -pthread on gcc 11.4, every one was run, and every number labeled as measured here comes from those runs on this machine, an Intel Xeon Platinum 8480+ with 52 logical cores visible. It is a shared virtualized host, so treat each figure as one honest sample with real scheduler noise rather than a lab result.

Threads and joining

A std::thread begins running the moment it is constructed, and the one rule that matters is that you must join() it before its destructor runs, otherwise the destructor calls std::terminate and the process dies. C++20 added std::jthread, which fixes the two chronic annoyances at once. Its destructor joins automatically, and it can hand your function a std::stop_token so the thread has a built-in, cooperative way to be told to finish up.

#include <chrono>
#include <iostream>
#include <thread>

using namespace std::chrono_literals;

int main() {
    // A plain std::thread must be joined (or detached) before it is destroyed,
    // otherwise the destructor calls std::terminate.
    std::thread t([] { std::cout << "worker: one unit of work\n"; });
    t.join();

    // std::jthread joins in its destructor and carries a stop token.
    std::jthread poller([](std::stop_token st) {
        int ticks = 0;
        while (!st.stop_requested()) {
            ++ticks;                       // poll something useful here
            std::this_thread::sleep_for(50ms);
        }
        std::cout << "poller: stopped after " << ticks << " ticks\n";
    });

    std::this_thread::sleep_for(250ms);
    poller.request_stop();   // the destructor would do both of these
    return 0;                // anyway: request_stop, then join
}

Run here, the poller reports five ticks and exits cleanly. The stop token is just a flag the thread polls at points of its own choosing, which is exactly the right amount of machinery. Forced thread cancellation is famously unsafe, and cooperative cancellation is what production code does anyway.

The escape hatch you should almost never take is detach(). A detached thread keeps running with no way to observe its completion, no way to receive its exceptions, and no join at program exit. When main returns, static destructors start tearing down globals while the detached thread may still be touching them, which is undefined behavior that surfaces as a one-in-a-thousand crash during shutdown. Every legitimate use I have seen is better served by a joined worker with a stop token, or by a thread pool that owns its threads and joins them in its destructor. If a value must outlive the function that started the work, that is what futures are for, not detach.

Sharing state safely

Two threads may both read a shared object without synchronization. The moment one of them writes, you need synchronization, and a program that skips it has a data race, which C++ defines as undefined behavior outright. Here is the smallest possible offender.

#include <iostream>
#include <thread>

long counter = 0;   // shared and unsynchronized: this is a data race

int main() {
    std::thread a([] { for (int i = 0; i < 1'000'000; ++i) ++counter; });
    std::thread b([] { for (int i = 0; i < 1'000'000; ++i) ++counter; });
    a.join();
    b.join();
    std::cout << counter << '\n';   // almost never 2000000
}

The runs are instructive. Built with -O2 on this machine the program printed 2000000 three times out of three, because the optimizer collapsed each loop into a single addition and the race window shrank to almost nothing. The program is exactly as broken as before, it just hides it. Built with -O0, where every increment really goes through memory, four runs measured here printed the following.

1063827
1043122
1019589
1000000

That last line lost an entire thread's million increments. This is why you never argue about a data race from observed output. You compile with ThreadSanitizer, g++ -std=c++20 -O1 -g -fsanitize=thread -pthread, and let it prove the race. Here is the report from a real run of the program above on this machine, trimmed to the lines that matter.

The fix for shared mutable state is a std::mutex owned next to the data it guards, locked through std::scoped_lock so an early return or an exception can never leave it held. When threads also need to wait for state to change, a std::condition_variable joins the pair, and there is one idiom you must treat as mandatory. Always wait with a predicate.

#include <condition_variable>
#include <deque>
#include <iostream>
#include <mutex>
#include <optional>
#include <string>
#include <thread>

class JobQueue {
    std::mutex m_;
    std::condition_variable cv_;
    std::deque<std::string> jobs_;
    bool closed_ = false;

public:
    void push(std::string j) {
        {
            std::scoped_lock lk(m_);
            jobs_.push_back(std::move(j));
        }                        // release before notifying
        cv_.notify_one();
    }

    void close() {
        {
            std::scoped_lock lk(m_);
            closed_ = true;
        }
        cv_.notify_all();
    }

    // wait() can return with no matching notify (a spurious wakeup), and
    // even after a real notify another thread may take the job first. The
    // predicate form re-checks the condition under the lock every time it
    // wakes, which makes both problems disappear.
    std::optional<std::string> pop() {
        std::unique_lock lk(m_);
        cv_.wait(lk, [&] { return closed_ || !jobs_.empty(); });
        if (jobs_.empty()) return std::nullopt;   // closed and drained
        std::string j = std::move(jobs_.front());
        jobs_.pop_front();
        return j;
    }
};

int main() {
    JobQueue q;
    std::jthread worker([&] {
        while (auto job = q.pop()) std::cout << "processed " << *job << '\n';
    });
    q.push("resize photo-001.png");
    q.push("resize photo-002.png");
    q.close();   // worker drains the queue, then pop() returns nullopt
}

The predicate loop is not defensive style, it is required for correctness. POSIX and every mainstream OS permit spurious wakeups, where wait() returns although nobody notified, because the alternative would make the primitive slower for everyone. On top of that, a genuine notify only means the condition was true at some point in the past. Between the notify and your wakeup another consumer may have taken the item. The predicate form is exactly a while loop around the wait, so a wakeup with a false condition simply goes back to sleep. Writing if where that while belongs is one of the classic concurrency bugs, and it passes tests for months before it fires. The theory page covers why the memory model makes the lock a synchronization point, which is what lets the woken thread trust what it reads.

A production-shaped thread pool

Spawning a thread per task stops scaling almost immediately, since thread creation costs tens of microseconds and a few thousand threads will drown the scheduler. The standard answer is a pool of long-lived workers pulling from a queue, and the whole thing fits in about seventy lines using only what the two sections above introduced. This listing is complete and compiles as shown.

#include <condition_variable>
#include <functional>
#include <future>
#include <memory>
#include <mutex>
#include <queue>
#include <stdexcept>
#include <thread>
#include <type_traits>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(unsigned n = std::thread::hardware_concurrency()) {
        workers_.reserve(n);
        for (unsigned i = 0; i < n; ++i)
            workers_.emplace_back([this] { run(); });
    }

    ~ThreadPool() { shutdown(); }
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    // Returns a future for the task's result. packaged_task is move-only
    // and std::function requires copyable targets, so the task lives in a
    // shared_ptr until std::move_only_function (C++23) is available.
    template <class F, class... Args>
    auto submit(F&& f, Args&&... args)
        -> std::future<std::invoke_result_t<F, Args...>> {
        using R = std::invoke_result_t<F, Args...>;
        auto task = std::make_shared<std::packaged_task<R()>>(
            std::bind(std::forward<F>(f), std::forward<Args>(args)...));
        std::future<R> fut = task->get_future();
        {
            std::scoped_lock lk(m_);
            if (closed_) throw std::runtime_error("submit on stopped pool");
            queue_.emplace([task] { (*task)(); });
        }
        cv_.notify_one();
        return fut;
    }

    // Graceful: accepts no new work, drains the queue, joins every worker.
    void shutdown() {
        {
            std::scoped_lock lk(m_);
            if (closed_) return;
            closed_ = true;
        }
        cv_.notify_all();
        for (auto& w : workers_) w.join();
    }

private:
    void run() {
        for (;;) {
            std::function<void()> job;
            {
                std::unique_lock lk(m_);
                cv_.wait(lk, [this] { return closed_ || !queue_.empty(); });
                if (queue_.empty()) return;   // closed and fully drained
                job = std::move(queue_.front());
                queue_.pop();
            }
            job();                            // run outside the lock
        }
    }

    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> queue_;
    std::mutex m_;
    std::condition_variable cv_;
    bool closed_ = false;
};

Three decisions carry the design. Tasks run outside the lock, so a slow task never blocks the queue. Shutdown flips closed_, wakes everyone, and each worker drains what remains before returning, so submitted work always completes and join is guaranteed. And submit wraps the callable in a std::packaged_task, whose future carries the return value or any thrown exception back to the caller.

#include "pool.hpp"   // the class above

#include <cstdint>
#include <iostream>
#include <vector>

static std::uint64_t spin_work(std::uint64_t seed, int iters) {
    std::uint64_t x = seed | 1;      // xorshift64, real CPU work
    for (int i = 0; i < iters; ++i) {
        x ^= x << 13; x ^= x >> 7; x ^= x << 17;
    }
    return x;
}

int main() {
    ThreadPool pool(32);
    std::vector<std::future<std::uint64_t>> futs;
    for (int i = 0; i < 20'000; ++i)
        futs.push_back(pool.submit(spin_work, (std::uint64_t)i, 100'000));
    std::uint64_t acc = 0;
    for (auto& f : futs) acc += f.get();
    std::cout << "checksum " << acc << '\n';
}   // pool destructor drains and joins

I benchmarked exactly this workload, 20,000 tasks of about 200 microseconds of arithmetic each, against a sequential loop. Measured here, with checksums verified equal on every run.

sequential          4036 ms
pool, 16 threads     257 ms   15.7x speedup
pool, 32 threads     131 ms   30.8x speedup   (152,805 tasks/s)
pool, 48 threads     112 ms   36.1x speedup

Scaling is essentially linear to 32 threads and tapers at 48 on this shared box. The more valuable measurement is the failure mode. With tiny tasks of about 4 microseconds each, 200,000 of them, the pool managed roughly 233,000 tasks per second and a speedup of 0.94, slower than the plain loop. A single mutex-guarded queue hands off a few hundred thousand tasks per second and no more, so tasks below a few microseconds are pure overhead. The fix is not a cleverer queue, it is batching, submit chunks of a few hundred small items as one task and the pool goes right back to scaling.

Atomics without folklore

An atomic operation is indivisible and never a data race, so std::atomic<long> is the correct minimal fix for the broken counter above. Every operation also carries a memory order, and the default, memory_order_seq_cst, is the strongest and the right starting point. The relaxations are for specific, justified patterns, and the first honest question is always whether the atomic is even the bottleneck. I measured eight threads doing a million increments each, all variants producing the identical final count.

mutex lock/unlock per increment    93.8 ns/op
atomic fetch_add, seq_cst          23.7 ns/op
atomic fetch_add, relaxed          22.7 ns/op
thread-local sum, one final add     0.03 ns/op

Two lessons, measured here. First, relaxed ordering bought about four percent over the default on this x86 machine, because an atomic increment's real cost is cores fighting over one cache line, not the memory fence. Choose relaxed when the semantics allow it, not for speed. Statistics counters are the canonical case, nothing else is ordered against the count and only the final total matters.

#include <atomic>

std::atomic<long> hits{0};

void worker(int n) {
    long local = 0;
    for (int i = 0; i < n; ++i) {
        // ... real work ...
        ++local;                     // no sharing in the hot loop
    }
    hits.fetch_add(local, std::memory_order_relaxed);   // one shared op
}

Second, the thread-local line is the real answer. Not sharing is three orders of magnitude cheaper than sharing politely, and that pattern, accumulate locally and combine once, is the shape of almost every fast parallel program. When ordering does matter, when a flag must publish data written before it, you need the acquire and release pair, and the theory page derives why. The ring buffer later in this article is a complete worked example.

Folklore also says spinlocks are fast. Here is the standard one, a correct test-and-test-and-set on std::atomic_flag, spinning read-only between attempts so waiters do not hammer the cache line.

#include <atomic>

class Spinlock {
    std::atomic_flag f_ = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (f_.test_and_set(std::memory_order_acquire))
            while (f_.test(std::memory_order_relaxed)) { /* spin read-only */ }
    }
    void unlock() { f_.clear(std::memory_order_release); }
};

Under the same eight-thread contended counter, measured here, the spinlock cost 110.8 ns per operation against 85.4 ns for std::mutex. The spinlock lost. Modern glibc mutexes already spin briefly before sleeping, so you get the fast uncontended path anyway, plus a scheduler that puts losing threads to sleep instead of burning cores, plus sane behavior when a lock holder gets preempted, which on a shared virtualized host like this one happens constantly. A spinlock earns its place only for critical sections of a few dozen nanoseconds with threads pinned to dedicated cores. The pool's mutex is the right default.

Async composition

std::async looks like the easy path, one call and you have a future. It hides a famous surprise. A future returned by std::async blocks in its destructor until the task completes, so if you discard the return value, the temporary future is destroyed at the end of the statement and your fire-and-forget call runs synchronously.

#include <chrono>
#include <future>
#include <iostream>
#include <thread>

using namespace std::chrono_literals;
using clk = std::chrono::steady_clock;

static double ms_since(clk::time_point t0) {
    return std::chrono::duration<double, std::milli>(clk::now() - t0).count();
}

int main() {
    // The trap: each temporary future joins in its destructor,
    // so these two "async" calls run one after the other.
    auto t0 = clk::now();
    std::async(std::launch::async, [] { std::this_thread::sleep_for(300ms); });
    std::async(std::launch::async, [] { std::this_thread::sleep_for(300ms); });
    std::cout << "discarded futures: " << ms_since(t0) << " ms\n";

    // Keeping the futures alive lets the two tasks overlap.
    auto t1 = clk::now();
    auto f1 = std::async(std::launch::async, [] { std::this_thread::sleep_for(300ms); });
    auto f2 = std::async(std::launch::async, [] { std::this_thread::sleep_for(300ms); });
    f1.get();
    f2.get();
    std::cout << "kept futures:      " << ms_since(t1) << " ms\n";
}

Measured here, the discarded version took 600.4 ms and the kept version 300.2 ms, the two sleeps serialized exactly as predicted. gcc even warns on the discarded calls because std::async is marked [[nodiscard]], a warning worth promoting to an error in CI. Two more habits worth adopting. Always pass std::launch::async explicitly, since the default policy lets the implementation defer the task until someone calls get(), which can mean it never runs concurrently at all. And remember that each call may spawn a fresh thread, so a loop submitting thousands of async tasks is a thread-per-task program with extra steps.

The primitive underneath is the std::promise and std::future pair, a one-shot channel that moves a value or an exception across threads. It is the right tool when a thread you already own must deliver one result, and promise::set_exception makes error propagation explicit. My rule of thumb has become simple. std::async is fine for a handful of coarse one-off tasks in application code, and everything with volume or a lifetime beyond one call site goes through the pool, which gives the same futures with owned, bounded threads and graceful shutdown.

Parallel algorithms

Since C++17 the standard algorithms accept an execution policy as their first argument, and this is the cheapest parallelism in the language. On gcc the parallel policies are implemented on top of Intel TBB, so the link line becomes g++ -std=c++20 -O2 -pthread par.cpp -ltbb, and without TBB installed the policies quietly compile to sequential fallbacks, which is worth verifying once with a stopwatch.

#include <algorithm>
#include <cmath>
#include <cstdint>
#include <execution>
#include <iostream>
#include <numeric>
#include <random>
#include <vector>

int main() {
    const std::size_t N = 50'000'000;
    std::mt19937_64 rng(7);
    std::vector<std::uint64_t> a(N);
    for (auto& v : a) v = rng();

    std::sort(std::execution::par, a.begin(), a.end());

    std::vector<double> in(N), out(N);
    for (std::size_t i = 0; i < N; ++i) in[i] = 1.0 + (double)(i % 1000);
    std::transform(std::execution::par_unseq, in.begin(), in.end(), out.begin(),
                   [](double x) { return std::sqrt(x) * std::log(x); });

    double total = std::reduce(std::execution::par, in.begin(), in.end());
    std::cout << a.front() << ' ' << out.back() << ' ' << total << '\n';
}

I ran each of these on 50 million elements, sequential policy against parallel, results verified identical. Measured here.

sort 50M u64        seq 5001 ms    par        183 ms    27.3x
transform 50M       seq  226 ms    par_unseq  8.8 ms    25.8x
reduce 50M          seq   35 ms    par        1.9 ms    18.8x

A 27x speedup on std::sort for the cost of one argument is remarkable, and par_unseq, which additionally permits vectorization within each thread, is the right choice for clean per-element math like the transform. The constraints are the flip side of the price. Your callables must not lock, allocate carelessly, or touch shared mutable state, since the library divides work across an internal thread pool however it likes. Exceptions escaping a parallel algorithm call std::terminate. And small inputs get slower, not faster, since splitting and joining has a fixed cost, so below roughly a hundred thousand cheap elements the sequential policy usually wins. Reach for these before writing any manual threading over a container, and drop to the pool only when the work is not shaped like one algorithm over one range.

Real patterns

The single most useful lock-free structure in practice is the bounded single-producer single-consumer ring buffer, the backbone of audio callbacks, logging shims, and network packet paths. One thread pushes, one thread pops, and correctness rests on a single acquire and release pair in each direction. The producer's release store to tail_ publishes the slot it just wrote, and the consumer's acquire load observes it, with the mirrored pair on head_ returning slots. Two refinements make it fast. The indices live on separate cache lines so the two cores stop invalidating each other on every operation, and each side keeps a cached copy of the other side's index so it only pays for a cross-core read when the ring actually looks full or empty.

#include <array>
#include <atomic>
#include <cstddef>

template <class T, std::size_t N>
class SpscRing {
    static_assert((N & (N - 1)) == 0, "N must be a power of two");

    alignas(64) std::atomic<std::size_t> head_{0};   // consumer position
    alignas(64) std::size_t cached_head_ = 0;        // producer's view of head_
    alignas(64) std::atomic<std::size_t> tail_{0};   // producer position
    alignas(64) std::size_t cached_tail_ = 0;        // consumer's view of tail_
    alignas(64) std::array<T, N> buf_{};

public:
    bool push(const T& x) {                    // producer thread only
        const std::size_t t = tail_.load(std::memory_order_relaxed);
        if (t - cached_head_ == N) {                          // looks full
            cached_head_ = head_.load(std::memory_order_acquire);
            if (t - cached_head_ == N) return false;          // actually full
        }
        buf_[t & (N - 1)] = x;
        tail_.store(t + 1, std::memory_order_release);        // publish slot
        return true;
    }

    bool pop(T& out) {                         // consumer thread only
        const std::size_t h = head_.load(std::memory_order_relaxed);
        if (h == cached_tail_) {                              // looks empty
            cached_tail_ = tail_.load(std::memory_order_acquire);
            if (h == cached_tail_) return false;              // actually empty
        }
        out = buf_[h & (N - 1)];
        head_.store(h + 1, std::memory_order_release);        // return slot
        return true;
    }
};

I pushed 100 million integers through a 1024-slot ring, checksum verified, with the two threads pinned to the two hardware threads of one physical core so they share a cache. Measured here, the cached-index version moved 389 million items per second, about 2.6 ns per item, while the same ring without the index caching managed 81 million. Placement dominates everything. Unpinned on this shared host, or pinned to two separate physical cores, throughput swung between roughly 16 and 94 million items per second from run to run as the hypervisor moved the threads around, which is itself the measurement to remember. Lock-free numbers are topology numbers.

Chain stages with queues and you have a producer-consumer pipeline. Between one producer and one consumer, use the ring above. Between many and many, use the mutex-and-condition-variable JobQueue from earlier, which at a few hundred thousand handoffs per second is nowhere near the bottleneck for stages doing real work. Keep every queue bounded so backpressure propagates upstream instead of becoming unbounded memory growth, and shut the pipeline down in flow order, close the first queue, let each stage drain and close the next.

For fan-out and fan-in, C++20 finally shipped the two primitives everyone reimplemented. A std::latch is a one-shot countdown, right for scatter work and gather once. A std::barrier is reusable and right for iterative algorithms where every thread must finish phase k before any thread starts phase k+1, and its completion function runs exactly once per phase in exactly one thread, the natural home for a reduction step.

#include <barrier>
#include <iostream>
#include <latch>
#include <numeric>
#include <thread>
#include <vector>

int main() {
    const int T = 8;
    const std::size_t N = 8'000'000;
    std::vector<double> data(N, 1.0);
    std::vector<double> partial(T, 0.0);

    // Fan-out/fan-in: T workers each sum a slice, main waits on the latch.
    std::latch done(T);
    std::vector<std::jthread> workers;
    for (int t = 0; t < T; ++t)
        workers.emplace_back([&, t] {
            const std::size_t lo = N / T * t, hi = (t == T - 1) ? N : N / T * (t + 1);
            partial[t] = std::accumulate(data.begin() + lo, data.begin() + hi, 0.0);
            done.count_down();
        });
    done.wait();   // count_down/wait synchronize, the partials are visible
    std::cout << "total = " << std::accumulate(partial.begin(), partial.end(), 0.0) << '\n';
    workers.clear();   // jthreads join here

    // Iterative phases: nobody starts phase k+1 until all finish phase k.
    int phase = 0;
    std::barrier sync(T, [&]() noexcept { std::cout << "phase " << phase++ << " done\n"; });
    std::vector<std::jthread> stages;
    for (int t = 0; t < T; ++t)
        stages.emplace_back([&, t] {
            for (int p = 0; p < 3; ++p) {
                for (std::size_t i = t; i < N; i += T) data[i] *= 0.5;
                sync.arrive_and_wait();
            }
        });
    stages.clear();
    std::cout << "data[0] = " << data[0] << '\n';   // 0.125 after 3 halvings
}

Run here it prints the total of eight million, three phase-done lines in order, and 0.125, each value confirming the synchronization it depends on. The latch's count_down and wait form a synchronization point, which is why the main thread may read the partial sums without any lock.

The debugging kit

ThreadSanitizer is the first tool and the one to wire into CI. Build with -fsanitize=thread -O1 -g, run your tests, and treat any report as a real bug, since TSan has essentially no false positives on correctly annotated code. It costs roughly 5x to 15x in speed and a lot of memory, which is why it is a test-suite tool rather than a production flag. One practical note from this very machine, on recent kernels with 57-bit address randomization TSan can abort at startup with an unexpected memory mapping error, and running the binary under setarch -R or lowering vm.mmap_rnd_bits fixes it. Valgrind's helgrind is the second opinion, no recompile needed, and on the racy counter from earlier it reported the same conflict as a possible data race between the two threads, at about 30x slowdown. It predates TSan and reports more possible races, so I reach for it when I cannot rebuild.

Name your threads the day you create them. Fifteen minutes of plumbing pays off every single time you open a debugger or top -H, because thread 7 of 48 tells you nothing and img-worker tells you everything.

#include <pthread.h>
#include <thread>

void start_named_worker() {
    static std::jthread worker([](std::stop_token st) {
        while (!st.stop_requested()) { /* work */ }
    });
    // 15 characters max plus the terminator, silently truncated beyond
    pthread_setname_np(worker.native_handle(), "img-worker");
}

The name shows up in /proc/PID/task/*/comm, in top -H, in gdb's thread list, and in TSan reports, which I verified here by reading the name back with pthread_getname_np.

Deadlocks are the one failure that gets easier when it happens, because a deadlocked process is frozen evidence. This program takes two mutexes in opposite orders on two threads and hangs almost every run.

#include <chrono>
#include <mutex>
#include <thread>

using namespace std::chrono_literals;

std::mutex accounts_mu;
std::mutex audit_mu;

void transfer() {                        // locks accounts, then audit
    std::scoped_lock a(accounts_mu);
    std::this_thread::sleep_for(10ms);
    std::scoped_lock b(audit_mu);
}

void report() {                          // locks audit, then accounts
    std::scoped_lock a(audit_mu);
    std::this_thread::sleep_for(10ms);
    std::scoped_lock b(accounts_mu);
}

int main() {
    std::thread t1(transfer);
    std::thread t2(report);
    t1.join();
    t2.join();
}

Reading it is mechanical. Find every thread parked in __lll_lock_wait, note which mutex each one wants, gdb even resolves the addresses to the symbol names, then ask who holds it. Thread 3 is inside report() wanting accounts_mu, which transfer() on thread 2 holds while wanting audit_mu, which thread 3 holds. That closed loop of wants is the deadlock, and main blocked in join is the bystander. The fix is a global lock order, or better, one std::scoped_lock(accounts_mu, audit_mu) acquiring both at once, since its deadlock-avoidance algorithm makes the opposite-order bug impossible to write.

A closing decision guide

The table below is how I actually choose, condensed from everything measured above.

SituationReach forBecause
One algorithm over one big containerstd::execution::par / par_unseq27x on sort measured here for one extra argument, no threads to manage
Many independent tasks, results neededThe thread pool with submitOwned threads, futures with exceptions, graceful shutdown, near-linear scaling for tasks over ~50 µs
Tasks under a few microsecondsBatch them, then the poolThe queue hands off ~233k tasks/s measured here, tiny tasks are pure overhead
A handful of coarse one-off jobsstd::async(std::launch::async, ...)Least code, fine at small scale, keep the futures and pass the policy
A long-lived background workerstd::jthread with a stop tokenCooperative cancellation and an automatic join, never detach
Shared mutable statestd::mutex + std::scoped_lockBeat the spinlock under contention measured here, correct under preemption
Waiting for state to changecondition_variable with a predicateSpurious wakeups make the predicate loop mandatory, not stylistic
A shared counter or flagstd::atomic, relaxed for pure stats4x cheaper than a mutex, and thread-local accumulation is 700x cheaper still
One producer, one consumer, hot pathThe SPSC ring buffer389M items/s measured here pinned, but placement decides everything
Scatter work, gather oncestd::latchOne-shot countdown, the fan-in synchronizes the results
Iterative phases in lockstepstd::barrierReusable, completion function runs once per phase
Any of the above, before shippingTSan in CIIt caught the race whose output looked correct three runs out of three

If one idea survives past the details, let it be this one. The fastest concurrent code in this article was never the cleverest synchronization, it was the design that shared the least, the thread-local counter, the batched tasks, the per-side cached index. Reach for structure first, primitives second, and let the measurements arbitrate. For why these primitives mean what they mean, the memory model write-up picks up exactly where this page stops.
